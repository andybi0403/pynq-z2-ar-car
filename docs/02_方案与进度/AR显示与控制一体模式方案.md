# AR 显示与控制一体模式方案分析

> 问题：想做成"AR 显示画面 + 控制"一体化模式，但小车会动，画面和控制怎么跟上？
> 结论先行：**PYNQ 和 STM32 都在车上，它们之间的 UART、摄像头 USB 线本来就是车上的短线，不受"车动"影响。真正被车动拖住的是三根外线——①控制端→PYNQ ②PYNQ→显示器 ③PYNQ 供电。把这三根外线解决掉就是一体化方案，不需要"全部无线"。**

## 1. 先理清哪些线真的会被"车动"影响

| 链路 | 物理位置 | 是否受车动影响 |
|---|---|---|
| PYNQ ↔ STM32（UART，K1 插座） | 车内，两板相邻 | ❌ 不受影响（30cm 排线） |
| USB 摄像头 → PYNQ | 车内 | ❌ 不受影响 |
| 编码器/超声波 → PYNQ Pmod B | 车内 | ❌ 不受影响 |
| **控制端（PC/手机）→ PYNQ** | 车外 | ✅ 受影响 |
| **PYNQ HDMI → 显示器** | 车外 | ✅ 受影响 |
| **PYNQ 供电** | 车外 | ✅ 受影响 |

所以问题不是"要不要 HDMI 线"，而是"这三根外线各自怎么处理"。

## 2. 方案对比

### 方案 A：USB WiFi 棒 + 网页一体化操控台（推荐主线）

PYNQ-Z2 的 USB Host 插一只 USB WiFi 网卡，PYNQ 开 AP 热点（或连手机热点），PC 浏览器打开一个页面同时完成 AR 观赛 + 操控 + 仪表：

```text
PC 浏览器（一个网页）
 ├── AR 画面：MJPEG 视频流（PS 软件叠加/状态仪表版；PL 叠加结果上网页需另加捕获通路，见下）
 ├── 控制面板：虚拟方向键/滑块 → HTTP POST → PYNQ → UART → STM32
 └── 状态仪表：$CAR 帧 + 编码器/超声波/风险等级，WebSocket 刷新
PYNQ ──UART── STM32（车内短线，不动）
```

- 实现：PS 端 Flask 约 100 行（MJPEG 推流参考 Miguel Grinberg 的线程生成器模式）。**必须澄清的视频通路限制：PL 的流式 OSD 叠加发生在 VDMA 读→HDMI 的数据流上，不会自动把叠加结果写回 DDR 帧缓存**；PS 直接压缩原 DDR 帧时，网页看到的是未叠加画面。两个可选路线：(a)【本阶段采用】网页画面由 PS 用 OpenCV 画同样的状态信息（软件叠加），HDMI 保持 PL 硬件叠加——网页是"软件叠加+状态仪表"，报告中不得声称网页直接搬运 PL 叠加帧；(b)【扩展项】增加 OSD 输出到 S2MM 的帧捕获通路（VDMA S2MM 或 AXIS-VideoDMA 写回）与缓冲同步，让网页拿到 PL 叠加后的帧——带宽翻倍（约 110MB/s），列为 F 阶段后的可选优化。FPGA 的核心算力合规性由 PL 的测速/测距/时间戳/风险机/硬件 OSD(HDMI 通路)承担，不依赖网页路线。
- 延迟量级：640×480 MJPEG 局域网约 80–200ms，P50/P95 需实测并写进指标表；控制指令 RTT 约 10–50ms，对低速车完全够用。
- 优点：成本≈一支 WiFi 棒（20–40 元）；正好对应方向三**拓展(5) 网络远程监控与数据传输**；一个网页即"AR+控制一体"，演示效果直观（评委手机也能扫进去看）。
- 风险与对策：
  - WiFi 棒驱动：选 RTL8188EU/8192CU 等常见芯片，**PYNQ 到货第一周列入兼容性验收清单**（`lsusb`→`dmesg`→`ip a`），不兼容则换手机 USB 网络共享兜底；
  - 场馆网络不可控：用 **PYNQ 自建 AP（hostapd）**，不依赖现场路由器；
  - WiFi 断连：显示和控制同时丢失，但 PL 风险状态机 + STM32 250ms 租约停车**独立生效**——这一点必须写进报告，是"两端协同 + 通信异常处理"的加分证据。

### 方案 B：无线 HDMI 图传套件（显示专用，零软件）

PL 叠加后的 HDMI 输出接 5.8GHz 无线 HDMI 发射器（约 200–500 元），接收器接场边显示器。

- 优点：零开发量、画质与延迟（30–100ms）优于 MJPEG，AR 画面就是真正的 HDMI 画面。
- 缺点：只是把 HDMI 线变无线，**控制链路仍要另解决**（还是得配方案 A 的 WiFi 或保留短网线）；车上多一套发射器要供电、要固定，加重小车；超出"多传感器融合"主线叙事。
- 定位：预算充足时的**演示增强件**，不是必需。

### 方案 C：5.8G FPV 模拟图传

延迟最低（<40ms）但需 AV 信号转接、画质差、无 OSD 数据通道，与"AR 高清叠加+量化指标"的评分方向不符。不推荐。

### 方案 D：全有线（HDMI 线 + 网线跟车）

室内 5–10m HDMI/网线可行，但绊线、转弯缠绕、演示观感差；只保留为 **PYNQ 到货初期的开发阶段形态**（车不动，线够长）。

## 3. 推荐组合（分阶段）

| 阶段 | 形态 | 说明 |
|---|---|---|
| C 阶段（板卡到货，车不动） | 全有线：网线 + HDMI + USB 供电 | 先把视频链路、传感器、OSD 全部跑稳 |
| F 阶段（低速整车） | **方案 A**：WiFi AP + 网页操控台；HDMI 只在验收台架近距离使用 | 一体化模式成型，采集 P50/P95 延迟数据 |
| 现场验收 | 主显示：场边 PC 大屏（网页）；可选：短 HDMI 备份 | WiFi 断链演示"安全停车"作为可靠性测试项 |

供电外线的解法（同样属于"车动"问题）：

- PYNQ-Z2 用**独立 12V 电池组（DC005 插头）**或符合 7–15V 要求的充电宝方案，固定在车上；不与原车三节 18650 并联（改装说明第 9 节原则不变）。
- 供电容量按"WiFi 棒 + 摄像头 + 板卡"峰值估算，验收前做 30 分钟连续运行温升/压降测试（正好是演示效果与可靠性指标的证据）。

## 4. 与评分细则的对应

| 评分项 | 一体化模式的贡献 |
|---|---|
| 性能评估 15 | MJPEG 延迟 P50/P95/最大值、控制 RTT、丢帧率（AMD 指标口径） |
| 操作界面 15 | 网页操控台=菜单+人机交互；HDMI AR 画面=信息显示 |
| 优化与改进 15 | "有线 HDMI vs WiFi 图传""PS 叠加 vs PL 叠加"两组对照数据 |
| 拓展灵活性 15 | 对应方向三拓展(5) 网络远程监控；PC/手机/平板多端接入 |
| 创新性 10 | PL 风险机 + 网页 AR + 双层安全闭环的整体叙事 |
| 演示效果 10 | 评委手机扫码看 AR 画面；WiFi 断链自动停车演示 |

## 5. 待实物确认清单（PYNQ 到货第一周）

1. USB WiFi 棒兼容性（首选 RTL8188EU，备选手机 USB 网络共享）。
2. hostapd 在 PYNQ 3.1 镜像上的 AP 模式可用性；不可用则退回"手机热点"模式。
3. MJPEG 推流帧率与延迟实测（640×480@15fps 起步）。
4. 独立 12V 供电下 WiFi+摄像头+HDMI 同时工作的电流裕量。
5. `$CAR` 状态经网页仪表显示的端到端延迟（串口 300ms 周期 + 推流延迟）。
