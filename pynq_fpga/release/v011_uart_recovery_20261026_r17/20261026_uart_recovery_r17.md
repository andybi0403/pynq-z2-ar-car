# r17 串口恢复候选

本候选用于验证 STM32 UART 的两个软件风险，不将其声明为实物根因或通信已修复。

- r14 在 2026-10-26 15:22 的初始状态和浏览器记录中持续收到真实 S1；首次下载握手失败、恢复应用仍零回包发生在 r16 写入之前。
- r14/r16 UART HWH 参数相同，准备脚本的 UART 配置相同；当前 PYNQ 已复核 UART/SLCR，并完整重启，重启后 UART1 接收计数仍为 0。
- 电脑 CH340 曾在 r16 写入前收到20条、写入后收到19条 CRC 有效 S1，不能以此代替当前 PYNQ 路径验收。
- 已烧录 r16 的程序会永久保留首个合法 Q1 的串口，并在另一 UART 输出 SAFE。新 ARM 回归在修改前复现三个失败：空闲旧端口不能交接、重复输入时另一 TX 仍输出、未使用 TX 并非高阻。

修复：上电双 UART 只接收，两个 TX 高阻；合法 Q1 选择一个发送器；另一 TX 保持高阻，不再向它发送 SAFE。原数据口连续2000ms没有合法查询，且锁车、两路实际 PWM 为0，另一口的合法 Q1 才能交接。交接清除旧请求及会话命令状态，保持锁车，解锁仍需新命令。错误CRC、杂字节、另一口的D1/R1及行驶中的Q1不能接管；两口STOP均有效。

12项 ARM 指令回归通过，包括双口真实主机收发、重复输入、空闲交接、坏CRC拒绝、行驶中禁止接管，以及双口紧急停止。该结果使用建模 MMIO/IRQ，不是硬件验收。主机、FPGA、红外仅告警和原完整控制台继承 r16；未重新综合 FPGA，未改变串口协议字段。

实际结果：未烧录、未部署，通信仍待恢复。候选包不自动启用行驶。烧录应沿用已成功的电脑扩展板 CH340 ROM 流程，写前整片备份、识别0410/128KiB、擦除前10页、写后整片比对；不发GO、R1或D1。之后 BOOT0=0 复位，再按原 PYNQ 方案实测查询。

本轮另修复 USB 调试脚本 sudo 认证的空读取误判，2项回归及重启后实际登录通过。这只影响调试传输，不能视为 STM32 通信根因。

原始证据：工作区 work/uart_regression_audit_20261026/；既往原始证据保留于 work/ground_trial_20261026/、work/ir_advisory_20261026/。板端 RTC 与电脑时间不同，时间线按电脑记录整理。
