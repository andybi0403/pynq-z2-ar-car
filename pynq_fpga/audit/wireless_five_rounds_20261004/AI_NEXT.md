# 下一步最推荐：可解释的AI多传感器AR驾驶助手

推荐把学习模型先放在已有电脑，异步读取已经显示的画面，每秒2—5次；PYNQ继续负责确定性的传感器融合、风险核与AR，STM32继续最终保护。无需再采购板卡、无线模块或供电模块。AI不拥有驾驶租约，不产生PREL，也不覆盖超声波/红外的故障。

故事：普通远程小车只提供摄像头；本项目能回答“眼前是什么、距离是否危险、为什么提示或停车”。模型给出场景语义，PL提供物理距离/轮速/制动边界，两者以同一frame_id关联到AR画面，并能回放一次事件的证据。契合已有申报“面向自动驾驶小车的智能感知与先进显示系统设计、方向三、多种传感器+AR辅助显示”；准确赛题评分仍以赛方最终文件为准。

## 第一阶段：场景分类与风险解释，优先做

使用MobileNetV3 Small对224×224缩略图做“可通行、行人/障碍附近、暗光、强反光、转弯/狭道”等经自采数据明确定义的场景分类。它是分类模型，不直接输出物体框或距离；ImageNet权重只作训练起点，不能宣称已经懂这些场景。结构及权重以[TorchVision官方MobileNetV3](https://docs.pytorch.org/vision/main/models/mobilenetv3.html)为准。

实现顺序：先采集分场景日志和有授权的训练图像，按不同采集日期/路线切分训练与测试，再训练/导出ONNX、固定模型SHA256、在电脑测推理延迟；只有模型效果通过才接入显示。纯本地运行，模型和运行库随离线包带齐。

最少新增接口：接收端在已有JPEG解码后，将少量缩略图交给独立Worker/电脑进程；新任务容量1，忙时替换旧任务。返回`session_id, frame_id, model_sha256, labels, scores, inference_ms, valid_until`。在服务端增加最大32项的帧元数据历史查询（只含传感器快照，不存32张原始帧）；结果找不到原帧、模型变更或超过500ms即舍弃，不能把旧框贴到新画面。

浏览器可从ONNX Runtime Web的WASM CPU后端起步，推理放在独立Worker，避免阻塞视频和50ms控制发送。[官方后端说明](https://onnxruntime.ai/docs/tutorials/web/)、[性能诊断与Worker建议](https://onnxruntime.ai/docs/tutorials/web/performance-diagnosis.html)。当前LAN使用HTTP，WebGPU还受浏览器安全上下文与GPU兼容性限制，不应将它作为本阶段前提；电脑Python/ONNX Runtime CPU进程也是可行实现路径。

风险解释第一版用可验证规则生成短句，例如：“前方距离120mm，低于当前速度对应制动边界；PL红色，STM32已锁存”。AI语义仅追加“识别为行人附近，置信度0.82”。故障原因来源必须是寄存器/实际CAR反馈，不能让语言模型编造距离或制动原因。这一步无需大模型和互联网。

验收：独立测试集各类precision/recall及混淆矩阵；不少于30段光照/遮挡/运动场景；连续30分钟视频+AI，与不开AI对照接收/绘制fps、P95显示延迟和控制RTT；AI任务队列永不超过1；无frame_id错贴；模型停止、错误或过时不影响本地保护。2—5Hz是初始预算，实际频率取电脑实测结果，不冒充板上性能。

## 第二阶段：事件回放与对照实验

增加停车前后5秒日志/视频事件缓存，容量和磁盘上限明确；保存传感器、PL风险、STM32反馈、AI置信度与视频档位变化，提供时间轴回放。用同一路线展示“只看视频”“只用单一传感器”“传感器融合AR”“融合AR+AI”四组，比较误提示、漏提示和操作者反应时间。由实验支持收益，不用演示故事替代指标。

## 第三阶段：把确实有价值的视觉前处理搬到PL

在整机720p30及资源余量经过实板验证后，优先迁移灰度、Sobel边缘、ROI统计或颜色分割；保持每拍1像素的AXIS接口与原始帧身份。当前完成候选的PL处理是历史帧元数据+前向AR+OSD，未含Sobel或神经网络加速器。不能因看到LUT空闲，就推断完整CNN能够直接塞进Zynq-7020或得到30fps。

不建议现阶段在双核A9上同时部署大模型、完整目标检测和720p JPEG；也不建议先购买额外AI板卡。先完成实板编码和无线验收，再决定哪一层值得加算力。
