# 第一轮：完整基线与视频稳定性

执行前测试计划：按 PLAN.md 第一轮矩阵，先运行所有既有 Python / STM32 C 回归和720p像素仿真；再注入摄像头一次读取异常后恢复，要求本地控制样本继续发布，画面错误有记录、远程驾驶撤销、不重放旧意图，恢复帧 ID 单调。检查最新完成版哈希与工作源码差异，并形成源码清单。

已发现反例：无线采集线程对摄像头拔出调用 JointRunner.fail，会置整个运行会话 stop_event。摄像头只服务监视画面，这种退出把视频故障耦合到本地控制服务，设备恢复后也没有重连入口。需保留明确 STOP 原因，但让感知/状态会话继续运行，并以有界退避重试摄像头。

修复：采集线程采用0.25—2秒有界退避重连，摄像头会话重建后重置设备序号比较、保持全局帧ID单调；坏JPEG丢弃并标故障，视频发布恢复清除故障。视频故障撤销远程控制并拒绝接管，本地采集/状态服务继续。DMA/控制结构性故障仍保留明确失败退出。

复验：round1_evidence/software.log 记录两套STM32 C、PC串口、105项host、102项preintegration测试与14种生产C故障矩阵通过。新断摄像头后恢复反例要求>=10次本地控制采样、恢复视频且没有继承意图。此前720p完整wrapper+回写适配器仿真通过921600像素。第一次无线构建确实因源改变被来源门禁拒绝，没有更新latest_candidate。
