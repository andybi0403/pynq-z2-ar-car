## 3. 硬件分工和正常接线基准

绿色板是编码器电平转换 PCB，电机尾部接白色六芯插头的小板才是编码器板。

```text
左前轮编码器 → 绿色板 J3 → SN74LVC245A → J1.LA3/LB3 → PYNQ JB1/JB2
右前轮编码器 → 绿色板 J4 → SN74LVC245A → J1.RA3/RB3 → PYNQ JB3/JB4
红外 / 超声波 → STM32 → UART → PYNQ
电机动力两根线 → 黑色 STM32 扩展板 TB6612，不经过绿色板
```

### 3.1 PYNQ 侧

这里 JA=PMODA、JB=PMODB；数字是**官方实体针号**，不是随观察方向从左往右数到的第几个孔。

| 绿色板丝印 | 原文要求 / 本轮选用位置 |
|---|---|
| J1.LA3 / LB3 / RA3 / RB3 | 依次→JB1 / JB2 / JB3 / JB4 |
| J1.GND | PYNQ 可靠 GND |
| J2.OEN | JA9，低有效使能 |
| J2.3V3 | Pmod 3.3V；本轮选 JA12 |
| J2.GND | GND；本轮选 JA11 |
| J5.5ENC | Arduino POWER J7 第4针，板上标 **5V** |
| J5.GND | PYNQ GND |

Pmod A/B：6、12=3.3V；5、11=GND；1、2、3、4、7、8、9、10 为信号脚。此前照片在“正对插孔、HDMI 在右”的方向，编号显示为：

```text
上排： 6   5   4   3   2   1
下排：12  11  10   9   8   7
```

这解释了为什么“从左数第6孔”可能其实是官方第1针。交接时必须看 pin1 标记，不能仅凭报数判断接错。

### 3.2 电机侧

| 编码器信号 | 左前 J3 | 右前 J4 |
|---|---|---|
| 负极 | GND | GND |
| A 相 | LA5 | RA5 |
| B 相 | LB5 | RB5 |
| 正极，4.5～5V | 5ENC | 5ENC |

六芯线最外两根是电机动力，中间四根是编码器电源和 A/B。**中间四根这一分组正确，并不等于四根针序已经正确。**

## 4. 本轮实际修改与尚缺的核验

1. **UART GND**：此前报告接 JB8，改至 JB11，JB9/JB10 插紧；随后 80/80 锁车查询通过。未隔离每项调整的贡献，不把所有问题归为一根地线。
2. **J5 编码器电源**：用户确认改接 PYNQ 标注 5V 的孔。旧照片的原落点不应写死为 RESET 或 3V3。尚无实测电压。
3. **J2 电源/使能**：改后正面照片支持 3V3→JA12、GND→JA11、OEN→JA9；后续用户又反馈 J1/J2/J5 均检查修改。接线位置核对不等于电压/焊点导通验收。
4. **J1 四路信号**：用户曾称 LA3 接“PMODB 6”，后来表示很可能原来按从左往右计数，并报告已检查修改。当前目标是官方 JB1～JB4；**最新修改没有逐根仪表确认或新的完整接后照片**。
5. **右前轮电源两线**：根据厂家同款手册图与两张右轮照片匹配视角，近景从上数第2根被识别为编码器正、第5根为编码器负。用户追线报告当时第2根→J4.GND、第5根→J4.5ENC，随后确认已交换；第3根→RA5、第4根→RB5 保留。
6. **左前轮**：用户确认自己当前视角下中间四根为负/B/A/正，分别接 J3.GND/LB5/LA5/5ENC，保持该接法。

**右侧极性判断来自厂家图的视角匹配＋用户追线，并非万用表独立确认。队友接手应优先核对电机实际型号、连接器正视/背视和板上丝印，再测实际通断/电压。不能把“已按指引换线”写成“电气测量证明正确”，也不能认定两侧都曾反接或已经烧坏。**

用户确认过手转时磁环跟随旋转，但这不是两侧完整机械、磁学、电气验收。

## 5. 测试方法是否可靠：边界要说清楚

### 5.1 最新手转测试读的是什么

脚本 `board_encoder_prepare.py`：确认服务 MainPID=0；映射 `0x43C00000`；验证 ID；写 CTRL bit0 发起快照，再读取 QEI_INFO。

- 左 QEI_INFO：`0x094`；右：`0x0AC`。
- bit1=`seen_edge`；bit2=`period_valid`；bits11:4 为非法跳变计数。
- 最新 epoch=490→491→492，说明快照序号确实递增。
- 源码 `car_qei.v` 中合法边沿会置 seen_edge=1，保持至复位；FILTER=0 时不受滤波等待门控。
- `car_qei_core.v` 直接打包上述标志，`car_perception_top.v` 在快照时直接锁存，**不由 SCALE 是否非零来门控这些标志**。

### 5.2 已纠正的误判

- SCALE=0 时测速批次和网页 `position_batch` 不更新，**不能用网页位置为0推断物理脉冲一定没有**。
- 能读到 STM32 UART 的红外/超声波数据，不等于 PMODB 编码器输入已通过直接高低电平正对照。
- GPIO 输出寄存器读回变化，不等于外部插孔电压已测量正确。
- J1 后来修改过，因此 13:50/14:22 的 GPIO 失败结果属于旧接线阶段，不能直接定位当前故障。
- 先前建议的 JA1→JA5 固定地测试、J1.LA3 线移到 J3.GND 的测试均已取消，**没有执行**。后者是在接收线真实落点未明确时提出的，若误接电源脚可能短路，不要根据旧日志照做。

## 7. 队友接手后的建议顺序

1. **先确认现场状态**：电池是否关闭、PYNQ 是否真正拔电、J3/J4 是否仍为正常四线还是已拔、临时线是否存在。15:44 后没有实物状态回执。
2. 断电核对 pin1 与 J1 四路端到端落点、J2、J5，以及右编码器供电极性；不要用左右照片的上下顺序直接互套。
3. 有表时先检查供电和共地：绿色板 J5.5ENC 的实际电压、J2.3V3、加载匹配 FPGA 后的 J2.OEN；再核对编码器端电源与慢转 A/B。通断档必须断电使用。
4. 若继续无表自检：隔离 J3/J4 两组编码器输入，在全断电、已确认 J1/J2/J5 后才布置 JA1→J3.LA5 临时线。该测试是临时诊断，不是正常接线；完成需恢复原车 FPGA 和线束。
5. 直接接收端正对照仍待完成。用已知的 0/3.3V 验证输入响应；不能将5V编码器原始信号直接送进PYNQ。只有通路与输入对照通过后，才适合归因编码器本体。
6. 物理边沿确认后再做方向、整圈计数、带载周长和 SCALE 标定。现在 SCALE 仍为0，不先用名义5362掩盖问题。

**本轮拟议的临时自检尚未实际接线/执行，不要把上面的计划当成已完成结果。** 随包诊断脚本不是一键启动器；尤其 `board_gpio_path_readback.py` 只能在对应隔离接法已核实后运行。base.bit 工作期间不能访问原车 `0x43C00000` 寄存器。
